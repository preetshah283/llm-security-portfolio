# Security Fundamentals: LLM Application Vulnerabilities

This module demonstrates how Large Language Models (LLMs) can act as conduits for classic web vulnerabilities. The core concept illustrated here is that **the LLM itself does not execute the attack**. Instead, the vulnerability lies in the application layer that blindly trusts, parses, or executes the untrusted output generated by the LLM.

Each script in this folder simulates a scenario where an attacker uses a prompt to coerce the LLM into generating malicious payloads.

## 1. Cross-Site Scripting (XSS) Simulation
**File:** `xss_simulation.py`  
**OWASP Mapping:** LLM02 (Insecure Output Handling)

**Overview:** 
Demonstrates how an LLM will obediently generate HTML/JavaScript containing malicious `<script>` tags when requested. If a frontend web application renders this raw output directly into the Document Object Model (DOM) (e.g., using `innerHTML`, `v-html`, or `dangerouslySetInnerHTML`), the attacker achieves Stored or Reflected XSS.

**Mitigations:**
- **Context-Aware Output Encoding:** Always encode LLM output before rendering it in the browser (e.g., convert `<script>` to `&lt;script&gt;`).
- **Use Safe APIs:** Use `innerText` or `textContent` instead of `innerHTML`.
- **Content Security Policy (CSP):** Implement strict CSP headers to block the execution of inline scripts.

## 2. SQL Injection (SQLi) Simulation
**File:** `sqli_simulation.py`  
**OWASP Mapping:** LLM01 (Prompt Injection) -> LLM02 (Insecure Output Handling)

**Overview:** 
Simulates an attack on a "Text-to-SQL" feature. The attacker uses prompt injection to override the original intent and append an `OR 1=1` clause while commenting out the rest of the query. If the backend executes this generated SQL string directly against the database, the attacker bypasses authentication or extracts unauthorized data.

**Mitigations:**
- **Never Trust LLM SQL Directly:** Treat LLM-generated SQL as untrusted input.
- **Parameterized Queries/ORMs:** If you must use LLM data to build queries, extract the *values* using structured JSON outputs (e.g., extracting just the username) and pass those values into parameterized DB queries rather than executing the raw string.
- **Principle of Least Privilege:** Ensure the database user account used by the application has strictly restricted permissions (read-only where possible).

## 3. Command Injection Simulation
**File:** `cmd_injection_simulation.py`  
**OWASP Mapping:** LLM08 (Excessive Agency) / LLM02 (Insecure Output Handling)

**Overview:** 
Highlights the danger of giving an LLM the agency to write and execute system commands. The attacker prompts the model to append `&& cat /etc/passwd` to a standard command. If the application blindly executes the LLM's response in a shell environment, the attacker gains Remote Code Execution (RCE) and can read sensitive system files.

**Mitigations:**
- **Avoid Shell Execution:** Do not pass LLM output into `os.system()` or `subprocess.run(shell=True)`.
- **Strict Allow-Listing:** If the LLM is meant to trigger system actions, map its outputs to a strict, hardcoded allow-list of safe functions rather than executing raw strings.
- **Sandboxing:** Execute any AI-generated commands inside an isolated, unprivileged container with no network access and restricted file system permissions.

## 4. Server-Side Request Forgery (SSRF) Simulation
**File:** `ssrf_simulation.py`  
**OWASP Mapping:** LLM07 (Insecure Plugin Design)

**Overview:** 
Targets Agentic LLMs equipped with web-fetching plugins. The attacker prompts the LLM to generate a URL pointing to the AWS metadata endpoint (`169.254.169.254`). If the LLM passes this URL to an insecure HTTP-fetching plugin, the plugin will retrieve the server's internal IAM credentials and the LLM will leak them back to the user.

**Mitigations:**
- **Network Segmentation (VPC):** Ensure the environment running the LLM plugins cannot route traffic to sensitive internal endpoints, metadata services, or loopback addresses (127.0.0.1).
- **Plugin Input Validation:** Implement strict validation at the plugin layer. If a plugin fetches URLs, explicitly block private IP ranges (RFC 1918) and cloud metadata IPs.
- **Enforce Mutual TLS / Authentication:** Internal services should require strong authentication, preventing an anonymous plugin request from succeeding.
